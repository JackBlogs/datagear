# DataGear V4.1 实现程度评估与后续实施计划

> 评估日期：2026-09-04
> 评估基线：《PRD-BI产品需求文档-V4.1-优化版》《SDS-软件开发说明书-V1.0》、原型 prototype.zip（14 页，与 self.deepvera.net/prototype 一致）
> 评估方式：PRD/SDS 全文精读 + 原型 HTML 分析 + Vue 源码走查 + 本地运行时逐页截图比对（localhost:5173，admin 登录）

## 一、总体结论（TL;DR）

| 维度 | 完成度 | 说明 |
|---|---|---|
| **前端视觉还原度** | **约 90%** | 原型 14 个页面全部有对应 Vue 实现，「能源暗域」风格、五组导航 IA（对齐 PRD 9.2）、顶栏/徽标/布局骨架高度还原 |
| **前端功能真实度** | 约 60% | 15+ 个原有功能页（数据源/数据集/图表/看板/用户/角色/驱动/插件/防护/SQL 工作台/导入导出）= 换肤不减功能，真实可用；7 个新页面为**纯演示页**（硬编码数据，无 API）；看板设计器为真实新实现（MVP 级） |
| **后端功能实现度** | 约 10% | 仅新增「数据大屏」一个全栈模块（约 475 行）；**PRD 最高优先级的语义层/指标中心后端为 0**；ChatBI、调度、告警、治理、开放 API 后端均为 0；Docker/备份恢复未开始 |
| **对照 PRD MVP 范围（12.2 节）** | 约 20% | 「已有基座确保稳定」部分完成；语义层最小闭环（Sprint 2/3）、调度/Docker/备份（Sprint 1）均未开始 |

一句话：**当前是「视觉层先行」的阶段性成果——壳已立、皮已换、旧功能完好；但 PRD V4.1 的灵魂（语义层驱动）还没动工，前端演示页与后端之间存在明显断层。** 下一步重心应从「还原原型」切换到「补语义层后端 + 演示页真实化」。

## 四、关键风险与断层

1. **演示页「看起来能用了」的风险**：指标中心/ChatBI/告警等页面按钮多为 Toast 占位（「规划中（演示）」），若直接给用户/领导演示，点两层就会穿帮。
2. **DDL 版本化纪律缺失**（大屏 500 的根因）：datagear.sql 直接追加建表语句，但运行库不会自动建表。SDS 3.1 要求新表走 DATAGEAR_VERSION 版本化增量，目前没有增量脚本机制被使用。
3. **首页指标卡区错位**：原型首页核心卖点是「关注指标卡（当前值+同环比+迷你趋势，PRD FR-SEM-06）」，当前实现为「资产数量卡」，语义层闭环建立后需回改。
4. **新路由未接权限**：新增 9 页路由未挂权限标识（stores/permissions 仅有旧模块），演示页上线前需处理。
5. **设计器渲染 bug**：顶栏/属性面板文字重叠（截图可见），疑为字体加载完成前截图+真实 CSS 重叠叠加，需排查。
6. **「演示数据」与真实数据无统一开关**：7 个演示页各自硬编码，后续真实化时需要逐页拆除，建议尽早抽象数据层。

## 五、后续实施计划（建议方案）

> 原则：与 PRD V4.1 的路径决策保持一致——**语义层先于 AI**（SD-02）、调度/Docker 先行（SD-05）、演示页真实化跟随后端交付节奏，每阶段以 PRD 验收标准收口。

### 阶段 0：正确性收口（0.5~1 周，立即做）
1. **修复大屏 500**：为 DATAGEAR_BIG_SCREEN 建立版本化增量脚本并执行（或开发期手动建表），验证分页/保存/设计器/展示全链路；给 /screen 列表页换肤（复用 datasource-page.css）。
2. **设计器渲染 bug**：排查顶栏/左栏/属性面板文字重叠与亮色底问题；补「预览模式」。
3. **类型与构建**：`npx vue-tsc --noEmit` 对本次新增/修改文件清零。
4. **演示数据开关**：抽一个 `useDemoData` 约定或统一「演示」徽标组件，为后续真实化留好替换点。
5. 大屏设计器接入真实图表部件（复用 ChartPreview），形成「大屏可用」闭环。

### 阶段 1：语义层与指标中心 MVP（4~6 人周，PRD 最高优先级）
**后端（新增 datagear-semantics 或挂 management 下的 metrics 包）：**
- 表：DG_DIMENSION / DG_MEASURE / DG_METRIC / DG_METRIC_VERSION / DG_GLOSSARY（按 SDS 3.4，走 DATAGEAR_VERSION 增量）
- Entity/Mapper/Service/Controller 四层；REST：`/api/metric/*`（CRUD、分页、目录、认证、版本）
- **指标查询引擎 v1**：原子指标（度量+聚合+口径）→ 参数化 SQL 编译，复用 Freemarker `${pc()}` 防注入；先不做派生指标/同环比的完整实现，但表结构预留
**前端：**
- MetricsView 从硬编码切真实 API；新建「指标定义向导」分步表单页（对齐 PRD 页面 2 交互说明：选数据集→维度/度量→属性→预览→保存）
- 指标详情抽屉接真实数据（概览/口径/版本；血缘可占位）
**消费闭环（PRD Sprint 3 验收）：**
- 设计器组件库增加「语义指标卡」；首页指标卡区改为关注指标（数值+同环比+迷你趋势）
- 验收：定义指标→SQL 工作台验证→看板/指标卡消费→同一指标多处出数一致；端到端 ≤30 分钟

### 阶段 2：调度基建 + 告警订阅（3~4 人周，PRD P0/P1）
- Quartz 引入（JobStore 持久化到系统库）、任务管理页（启停/日志/重试）
- 告警规则 CRUD + 阈值检测 Job + 邮件/Webhook/站内信通道 + 告警记录/静默
- AlertView 从演示切真实 API；对齐 FR-ALERT-01/03/04/05/06
- 同阶段顺手交付 **Docker 镜像 + compose + 备份恢复脚本**（FR-DELIV-01/02，0.5~2 人周，PRD 定为 P0）

### 阶段 3：ChatBI（8~12 人周，依赖阶段 1）
- 按 docs/ai-chatbi 方案落地：新增 datagear-ai（可选装配，无 LLM 配置自动隐藏）
- 通道 A 先行：大模型只做意图理解，工具化为「数据集/指标查询」，全程继承授权体系
- `/api/ai/chat` SSE 流式；ChatbiView 接后端（三段式回答、取数逻辑折叠、多轮上下文、澄清按钮、历史）
- BYO-LLM 配置页（Key 加密存储）；术语库管理页（表已在阶段 1 建）

### 阶段 4：治理 / 开放 API / 移动端真实化（按优先级插空）
- 治理 v1：元数据采集（复用 datagear-meta 解析）→ 数据字典 + 敏感字段识别；质量/血缘随调度与语义层成熟后再上
- 开放 API：指标/数据集发布为 REST + API Key 鉴权（依赖阶段 1 的指标 API）；嵌入签名 JWT + Embed SDK（P1）
- 移动端：H5 消费页（看板查看/问数/消息）响应式适配，先覆盖 PRD「消费类场景移动可用」口径
- 统计报表/填报/大屏深化：按 PRD 维持 P3/企业版定位，不投入

### 横切工程纪律（贯穿所有阶段）
- **DDL 版本化**：任何新表必须配 DATAGEAR_VERSION 增量脚本 + 回滚 SQL（大屏 500 的教训）
- **后端四层 + /api 前缀**：遵循 SDS 4.1 的 Controller/Service/Manager/DAO 约定；新资源类型接入现有 Authorization 资源级授权
- **前端**：新页面沿用 PAGE_CONVERSION_GUIDE 的「换肤不减功能」纪律；演示→真实的替换以 API 模块（src/api/*.ts）为唯一边界
- **测试**：指标 SQL 编译单测（对齐 SDS Spike② 通过标准）；每阶段跑通 vue-tsc 与后端编译

|---|---|---|---|
| 0 | 大屏修复/设计器打磨/类型清零 | 0.5~1 周 | — |
| 1 | 语义层与指标中心 MVP + 消费闭环 | 4~6 人周 | Sprint 2/3、FR-SEM-01/02/03/06 |
