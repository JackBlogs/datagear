# 产品概述
## 产品背景
随着企业数字化转型深入，数据已成为核心生产要素。但多数企业面临数据分散、指标口径不一、取数依赖技术人员、传统BI部署成本高等痛点。DataGear 作为开源轻量BI平台，已具备数据接入、数据集、70+图表、自由看板等基础能力，但在语义层、自助分析、企业级治理、AI增强分析等方面存在差距。
本PRD定义 DataGear 从「数据可视化看板工具」升级为「语义层驱动的一站式BI平台」的完整需求，覆盖数据接入、存储、治理、建模、分析、展示、分享全链路，并为二次开发明确方向与路径。
## 产品目标
| 目标维度 | 具体目标 | 衡量指标 |
| 业务目标 | 成为开源BI领域语义层+AI增强分析的标杆产品 | GitHub Star年增长≥50%、企业版付费转化率≥15% |
| 功能目标 | 补齐语义层、告警订阅、开放API、行列权限、AI问数五大核心能力 | P0功能100%交付、P1功能80%交付 |
| 体验目标 | 业务人员零SQL完成80%的常规分析需求 | 自助分析使用率≥60%、问数准确率≥85% |
| 性能目标 | 常规查询亚秒级返回，百万级数据P95≤3秒 | 看板加载P95≤3s、指标查询P95≤3s |
| 生态目标 | 支持嵌入第三方系统，提供数据API与MCP接口 | 嵌入SDK月下载≥5000、API月调用≥100万次 |
## 产品定位
DataGear 是一款开源免费、轻量、可私有化的"语义层驱动"商业智能（BI）分析平台：以数据集语义层与指标中心为地基，向上支撑自由看板、自助分析与AI增强分析（ChatBI），向外以开放API/嵌入SDK/MCP供给数据与指标，覆盖「接入→存储→治理→建模→分析→展示→分享」完整数据链路，服务中文场景与信创环境。
## 产品范围
本期范围（做）：
● 语义层与指标中心：维度/度量/指标定义、目录、认证、版本、血缘、统一消费、开放API
● AI增强分析（可插拔）：智能问数（Text2DSL）、AI解读、归因分析、BYO-LLM配置
● 数据告警与订阅推送：调度框架、阈值告警、看板/报表订阅、多渠道通知
● 数据交换与开放API：数据API服务、签名Token嵌入、Embed JS SDK、MCP Server
● 系统管理增强：行/列级数据权限、动态脱敏
● 交付与部署：Docker镜像、备份恢复、项目导入导出
● 综合首页：数据门户、工作台、全局搜索、收藏、首页组件库
明确不做（边界）：
● 不做独立重型ETL/数据集成产品；只做数据集内轻量数据准备，重ETL交由上游（SeaTunnel/Flink CDC等）
● 不做SaaS多租户云平台；坚持私有化单体+可选外置库高可用
● 不做自研OLAP引擎；以"直连实时OLAP+缓存加速"双轨应对实时化
● 不做裸text-to-SQL问数；坚持"语义层grounding+DSL中间层"的确定性路线
## 产品价值
● 安全稳定：私有化部署、数年迭代、基于角色的权限、数据默认私有、加密脱敏。
● 口径统一：语义层与指标中心保障"一个指标一个口径"，贯穿图表、报表、告警与AI问数。
● 功能丰富：多源接入、六类数据集、70+图表、GIS/三维/大屏、报表、模板化看板。
● 智能易用：可视化查询构建器、智能问数（ChatBI）、AI解读与归因，业务零SQL自助。
● 治理可控：元数据、数据标准、数据质量、数据血缘、指标认证一体的轻量数据治理。
● 易于扩展：运行时数据源驱动、自定义图表插件、开放看板API、数据API、嵌入SDK与MCP。
● 自由制作：原生HTML模板、可视化/源码编辑、多端响应式、联动钻取。
## 战略支点与产品边界
三个战略支点：
● 语义层优先：指标中心是ChatBI准确率、告警、嵌入、治理的共同地基，作为最高优先级的全新建设模块。
● AI可插拔而非重写内核：对标SQLBot，智能问数做成独立可插拔模块（复用现有数据集/权限体系），支持DeepSeek/Qwen/OpenAI兼容接口的自带模型（BYO-LLM）。
● 开放与嵌入放大生态：签名Token嵌入、数据API、MCP Server三层开放，让DataGear可被第三方系统与AI Agent消费。
## 名词解释
| 术语 | 含义 |
| 数据源 | 注册到系统的外部数据库连接信息 |
| 数据集 | 图表/看板/报表消费的统一数据抽象 |
| 语义层 | 在数据集之上统一声明维度/度量/指标/术语的模型层，一处定义多处消费 |
| 指标中心 | 指标的定义、目录、认证、版本、血缘与统一消费的功能集合 |
| 指标 | 统一口径的业务度量；原子指标=度量+聚合，派生指标=四则运算/同环比/占比/累计 |
| DSL | 大模型意图到确定性查询之间的结构化指令（指标/维度/筛选/排序/时间窗） |
| ChatBI | 对话式商业智能，用户通过自然语言提问获取数据洞察 |
| BYO-LLM | 自带大模型：用户配置自己的OpenAI兼容接口（DeepSeek/Qwen/GLM/私有模型） |
| 签名Token嵌入 | 第三方系统以共享密钥签发时效JWT，免登嵌入看板/报表的方式 |
| MCP | Model Context Protocol，让外部AI Agent以标准协议消费BI资产的开放接口 |
| 信创 | 信息技术应用创新：国产芯片/OS/数据库/中间件/浏览器的全栈适配要求 |
| 行级权限 | 按组织/字段值过滤可见数据行 |
| 列级权限 | 限制可见字段，敏感列按角色隐藏 |
| Persona | 用户画像，对目标用户的典型特征、目标、痛点的具象化描述 |
| 用户旅程 | 用户完成特定目标的端到端体验流程，包含行为、触点、情绪、痛点 |
| 用户故事 | 从用户视角描述功能需求的简短格式：作为<角色>，我希望<功能>，以便<价值> |
| 用例 | 对系统功能的详细描述，包含参与者、前置条件、主流程、备选流程、异常流程、后置条件 |
| MVP | Minimum Viable Product，最小可行产品，用最少的功能验证核心价值假设 |
| 灰度发布 | 分阶段逐步扩大新版本用户范围的发布策略，降低风险 |

## 核心业务流程
流程1：数据接入→治理→建模→展示主流程
| 步骤 | 操作角色 | 操作内容 | 系统响应 | 输出物 |
| 1 | 数据工程师 | 配置数据源（数据库/文件/HTTP/实时流），测试连接 | 连接校验、驱动加载、密码加密存储 | 数据源注册成功 |
| 2 | 数据工程师 | 执行元数据采集，定义数据标准和质量规则 | 自动采集库/表/列元数据，质量规则可配置 | 元数据目录、数据标准、质量规则 |
| 3 | 数据分析师 | 创建数据集（SQL/HTTP/CSV/Excel/JSON），定义字段和参数 | 数据集模板解析（Freemarker）、参数化查询、缓存配置 | 可复用数据集 |
| 4 | 数据分析师 | 在语义层定义维度/度量/指标，认证发布 | 指标查询引擎编译为参数化SQL，指标目录管理 | 统一定义的指标 |
| 5 | 数据分析师 | 创建图表（选插件、绑定数据集/指标、数据标记） | 70+图表渲染、一图多数据集、实时预览 | 图表部件 |
| 6 | 数据分析师 | 组装看板（HTML模板+图表部件+联动/钻取/筛选） | 拖拽布局、联动配置、钻取层级、响应式 | 可发布看板 |
| 7 | 管理员/分析师 | 配置权限（资源级/行级/列级）、脱敏规则 | 权限模型扩展、查询改写、动态脱敏 | 安全可控的访问控制 |
| 8 | 分析师/管理员 | 发布分享（密码分享/签名Token嵌入/链接/数据API） | 分享密码、JWT签发、API Key、白名单 | 多渠道分享与嵌入 |
| 9 | 业务人员/决策层 | 终端消费（PC/移动/大屏），下钻分析，智能问数 | 多端响应式、实时刷新、下钻联动、ChatBI | 数据洞察与决策支持 |
| 10 | 系统 | 主动触达（阈值告警/订阅推送/指标关注动态） | 调度框架定时执行、多渠道通知、快照渲染 | 主动数据服务 |
流程2：智能问数（ChatBI）详细流程
| 步骤 | 操作角色 | 操作内容 | 系统响应 | 异常处理 |
| 1 | 业务人员 | 在问数框输入自然语言问题（如"上月各区域销售额同比"） | 接收问题，进入问数流程 | 问题为空时提示输入 |
| 2 | 系统 | 知识库检索（RAG） | 检索术语库、同义词、业务规则、golden queries、认证答案 | 无匹配时进入通用意图识别 |
| 3 | 系统 | 大模型意图理解与拆解 | BYO-LLM解析问题，识别指标、维度、筛选、排序、时间窗 | 模型调用失败时返回友好提示，建议换种问法 |
| 4 | 系统 | 生成中间DSL | 将意图转化为结构化DSL（指标/维度/筛选/排序/时间窗） | DSL生成失败时展示澄清问题，主动追问 |
| 5 | 系统 | 命中认证答案判断 | 检查是否匹配golden queries或认证答案 | 未命中时继续执行查询 |
| 6 | 系统 | 指标查询引擎执行 | DSL→指标定义解析→编译为参数化SQL→行列权限改写→动态脱敏→执行→缓存 | 查询超时/失败时展示错误原因，建议缩小范围 |
| 7 | 系统 | 返回三段式回答 | 图表+数据表格+自然语言结论+取数逻辑说明 | 数据为空时展示空状态，建议调整筛选条件 |
| 8 | 业务人员 | 多轮追问/澄清 | 上下文管理，继续提问（如"华东区呢"、"按门店细分"） | 上下文丢失时提示重新描述 |
| 9 | 业务人员 | 一键转图表/看板/分享 | 将问数结果保存为图表或添加到看板，生成分享链接 | 保存失败时提示重试 |
流程3：指标查询（语义层）详细流程
| 步骤 | 操作内容 | 处理逻辑 | 输出 |
| 1 | 指标消费方提交查询 | 图表/报表/告警/问数/外部API提交「指标+维度+筛选+时间窗」 | 查询请求 |
| 2 | 指标定义解析 | 从指标中心读取指标定义（口径、聚合方式、派生公式、同环比计算） | 解析后的指标逻辑 |
| 3 | 编译为参数化SQL | 将指标+维度+筛选编译为SQL，复用${pc()}预编译机制，防注入 | 可执行SQL |
| 4 | 行列权限改写 | 根据当前用户角色/组织，在行级过滤条件中追加权限规则，列级隐藏敏感列 | 权限改写后的SQL |
| 5 | 动态脱敏 | 对剩余可见列中的敏感字段应用脱敏规则（掩码/截断/替换/哈希） | 脱敏后的结果集 |
| 6 | 执行与缓存 | 执行SQL，检查数据集级缓存策略，命中缓存直接返回，未命中执行并缓存 | 结构化结果数据 |
| 7 | 返回结果+口径元信息 | 返回数据+指标口径信息（供透明化展示），包含查询耗时、缓存命中状态 | 最终结果+元信息 |
流程4：告警与订阅推送流程
| 步骤 | 操作角色 | 操作内容 | 系统响应 | 输出 |
| 1 | 业务人员/管理员 | 配置告警规则（选择指标+阈值条件+检测频率+通知渠道+接收人） | 规则校验、保存到调度框架 | 告警规则 |
| 2 | 业务人员 | 配置订阅（选择看板/报表+频率+推送时间+格式+渠道） | 订阅保存、关联调度任务 | 订阅任务 |
| 3 | 系统 | 调度框架定时触发 | Quartz按cron触发告警检测和订阅生成 | 任务执行 |
| 4 | 系统 | 告警检测/快照生成 | 告警：执行指标查询→阈值判断；订阅：无头浏览器渲染看板截图/PDF/Excel | 告警结果/快照文件 |
| 5 | 系统 | 通知发送 | 通过邮件/Webhook/站内信/企微/飞书发送通知，包含指标值、阈值、链接/附件 | 通知消息 |
| 6 | 系统 | 静默与去重 | 检查静默期配置，同一异常在静默期内不重复告警 | 去重后的通知 |
| 7 | 用户 | 接收并处理 | 用户收到通知，点击链接直达看板/报表，查看详情和归因，标记已处理 | 告警处理记录 |
| 8 | 系统 | 历史留存 | 告警记录、订阅历史、执行日志持久化，可查询和审计 | 历史记录 |
流程5：签名Token嵌入流程
| 步骤 | 操作角色 | 操作内容 | 系统响应 | 输出 |
| 1 | 管理员/开发人员 | 在嵌入管理页面生成嵌入密钥（共享密钥+白名单+过期时间） | 密钥生成、加密存储、白名单配置 | 嵌入密钥 |
| 2 | 开发人员 | 第三方后端用共享密钥签发JWT（含用户ID、组织、资源ID、参数、过期时间） | JWT标准签发，HS256签名 | 时效Token |
| 3 | 开发人员 | 前端调用DataGearEmbed.render(dom, {resource, token, theme, params}) | JS SDK加载、Token校验、资源加载 | 嵌入初始化 |
| 4 | 系统 | Token认证与校验 | Spring Security过滤链校验JWT签名、过期时间、白名单、资源权限 | 认证通过/拒绝 |
| 5 | 系统 | 行级权限透传 | 从Token中提取用户/组织属性，自动套用行级数据权限和列级脱敏 | 权限过滤后的数据 |
| 6 | 系统 | 白标渲染 | 隐藏DataGear品牌元素（logo/链接/页脚），应用自定义主题色 | 白标看板 |
| 7 | 用户 | 在第三方系统中交互 | 用户在嵌入看板中进行下钻、联动、筛选、导出等操作 | 无缝交互体验 |
| 8 | 系统 | 调用监控与审计 | 记录嵌入调用日志、Token使用情况、异常访问 | 监控与审计数据 |
流程6：权限校验流程
请求 → 身份识别（会话/API Key/签名Token/匿名）→ 功能权限（角色/菜单校验）→ 资源级数据权限（Authorization表：资源×主体×权限值）→ 行级数据权限（按组织/字段值过滤）→ 列级数据权限（敏感列隐藏）→ 动态脱敏（按角色脱敏规则）→ 业务执行 → 结果返回（已脱敏数据）。
流程7：数据集查询（参数化）流程
看板/图表/报表请求 → 携带参数值（DataSetQuery）→ 数据集模板解析（Freemarker，${param}/${pc(param)}）→ 连接数据源执行（SQL/HTTP/文件读取）→ 结果结构化（字段映射、类型转换、附加数据）→ 返回DataSetResult → 图表/报表渲染。

# 用户交互设计
## 交互设计原则
● 一致性：相同功能在不同页面交互方式一致，相同操作有相同反馈
● 即时反馈：用户操作后≤200ms给出视觉反馈，加载状态明确展示
● 容错性：危险操作有二次确认，误操作可撤销，错误提示可理解
● 渐进式：复杂功能分步引导，新手有引导，老手可跳过
● 可访问性：支持键盘操作，颜色对比度符合WCAG AA，支持屏幕阅读器
● 移动端优先：核心功能在移动端可用，手势交互自然
## 全局交互规范
| 交互类型 | 规范 | 示例 |

## 差距分析结论
● DataGear的强项在"自由看板+插件体系+轻量部署"，弱项在"语义层、自助分析、企业级治理、开放集成"——与Superset（SQL深度强/业务自助弱）、Metabase（自助与嵌入强/治理弱）形成错位竞争空间
● 多数规划项属于"全新建设"而非"增强现有"，二次开发必须按基建（调度/邮件/开放API/权限扩展）→语义层→AI/告警/嵌入的顺序推进，不能并行摊大饼
● DataEase/SQLBot已验证"简单好用+可插拔问数+增值包"路径；DataGear的差异化空间在「中文场景+轻量私有化+数据集语义层+可嵌入+AI可插拔」的组合

## 技术架构概要
● 后端：Java 8 + Spring Boot 2.7 + Spring Security + MyBatis + Freemarker模板引擎；模块化分层（datagear-core/connection/analysis/dataexchange/persistence等）；新增datagear-semantics（语义层）、datagear-ai（AI可插拔）、datagear-scheduler（调度）子模块
● 前端：jQuery + Vue3 + PrimeVue + Freemarker服务端渲染混合架构；ECharts 5.6图表库；CodeMirror代码编辑器；新模块一律Vue3组件化
● 存储：内置Derby（开发/开箱即用）/外置MySQL（生产推荐）；Caffeine本地缓存；可选Redis分布式缓存
● 调度：Quartz（持久化JobStore到系统库），支撑告警/订阅/报表定时/数据抽取
● AI：BYO-LLM架构，通过OpenAI兼容接口调用DeepSeek/Qwen/GLM/私有部署模型；核心零LLM依赖，无配置时AI模块自动隐藏
● 开放：Spring Security过滤链支持会话/API Key/签名JWT三种认证通道；RESTful API + MCP Server
● 部署：单war包内嵌Tomcat / Docker单容器 / 外置WAR；配置外置（application.properties + 环境变量）

# MVP规划与实现
## MVP定义与目标
MVP（Minimum Viable Product，最小可行产品）目标：用最少的功能验证"语义层驱动的一站式BI平台"的核心价值假设，即：业务人员能否零SQL自助取数？指标统一定义能否解决口径不一致问题？嵌入能力能否被第三方系统快速集成？
| 维度 | MVP目标 | 验证指标 | 目标值 |
| 核心价值 | 验证语义层+指标中心的可用性 | 指标创建到看板引用的完成率 | ≥90% |
| 核心价值 | 验证零SQL自助取数 | 业务人员通过问数/拖拽完成取数的比例 | ≥60% |
| 核心价值 | 验证嵌入集成能力 | 第三方系统嵌入看板的集成时间 | ≤1人天 |
| 技术可行性 | 验证轻量部署体验 | Docker一键部署到可用的时间 | ≤5分钟 |
| 技术可行性 | 验证调度基建稳定性 | 定时任务7天连续运行成功率 | ≥99.5% |
| 用户体验 | 验证核心流程流畅度 | 从数据源接入到看板发布的端到端时间 | ≤30分钟 |

## 灰度发布策略与回滚方案
| 阶段 | 范围 | 持续时间 | 验证重点 | 回滚条件 |
| 内部灰度 | 开发/测试团队、内部dogfood环境 | 1周 | 功能完整性、性能基线、Bug修复 | P0/P1 Bug>5个或性能下降>20% |
| 种子用户 | 开源社区活跃用户、志愿者（5--10家） | 2周 | 真实场景验证、用户体验反馈、兼容性 | 核心功能不可用或数据丢失风险 |
| 公测版本 | 开源社区全量（标记为beta/RC） | 2--4周 | 大规模稳定性、性能、安全、文档 | 严重安全漏洞或数据损坏 |
| 正式发布 | 全量发布（稳定版） | 持续 | 持续监控、快速迭代补丁 | — |
回滚方案：版本升级前自动备份系统库和DATAGEAR_HOME，支持一键回滚到上一版本；DDL版本化升级（DATAGEAR_VERSION），每个版本有对应的回滚SQL脚本；Docker部署支持tag回滚；配置文件外置，升级不覆盖用户自定义配置；重大版本变更提供升级向导和检查清单，升级前自动校验兼容性。
## 路径决策逻辑（为什么是这个顺序）
● 调度/嵌入/Docker先行：成本最低、所有后续模块依赖调度，且嵌入与Docker立即改善开源用户获取与集成体验（对标Metabase的成功要素）
● 语义层先于AI：国内外调研一致结论——无语义层的ChatBI等于"演示玩具"（AtScale基准：无grounding错误率约80%）；指标中心同时反哺告警、开放API、首页，一次投入四处受益
● 告警/订阅/API紧跟语义层：三者都消费指标模型，打包建设边际成本最低，且都是"可感知、可演示"的刚需能力
● 问数V1放在Phase 2：此时语义层、术语库、行列权限均已就位，问数可做到"可解释、可干预、可认证"，避免裸NL2SQL的信任崩塌
● 报表/填报压轴且商业化：工程量最大（15--25人周）且是国内公认付费点（DataEase将填报放入收费X-Pack），适合作为企业版锚点而非开源核心的早期负担

| 指标 | 统一口径的业务度量；原子指标=度量+聚合，派生指标=四则运算/同环比/占比/累计 |
| 语义层 | 在数据集之上统一声明维度/度量/指标/术语的模型层，一处定义多处消费 |
| 指标中心 | 指标的定义、目录、认证、版本、血缘与统一消费的功能集合 |
| 业务术语库 | 字段/指标的同义词、业务用语与规则说明，ChatBI的grounding基础 |
| DSL | 大模型意图到确定性查询之间的结构化指令（指标/维度/筛选/排序/时间窗） |
| golden queries | 金标准问答对，用于问数知识库召回与准确率评估 |
| 认证答案 | 管理员认证的标准回答，用户提问命中时直接返回 |
| 数据脱敏 | 对敏感数据做变形处理以保护隐私 |
| 签名Token嵌入 | 第三方系统以共享密钥签发时效JWT，免登嵌入看板/报表的方式 |
| MCP | Model Context Protocol，让外部AI Agent以标准协议消费BI资产（指标/数据集）的开放接口 |
| BYO-LLM | 自带大模型：用户配置自己的OpenAI兼容接口（DeepSeek/Qwen/GLM/私有模型） |
| 信创 | 信息技术应用创新：国产芯片/OS/数据库/中间件/浏览器的全栈适配要求 |
| 行级权限 | 按组织/字段值过滤可见数据行 |
| 列级权限 | 限制可见字段，敏感列按角色隐藏 |
| Persona | 用户画像，对目标用户的典型特征、目标、痛点的具象化描述 |
| 用户旅程 | 用户完成特定目标的端到端体验流程，包含行为、触点、情绪、痛点 |
| 用户故事 | 从用户视角描述功能需求的简短格式：作为<角色>，我希望<功能>，以便<价值> |
| 用例 | 对系统功能的详细描述，包含参与者、前置条件、主流程、备选流程、异常流程、后置条件 |
| MVP | Minimum Viable Product，最小可行产品，用最少的功能验证核心价值假设 |
| 灰度发布 | 分阶段逐步扩大新版本用户范围的发布策略，降低风险 |
| NPS | Net Promoter Score，净推荐值，衡量用户满意度和忠诚度的指标 |
